# Private media and publication

Migration 003 supersedes the 002-only publication refusal with **conditional delivery from a private bucket**. It requires owner review and real staging Storage verification before enabling writes. No production SQL or media operation was executed.

New uploads stay in `draft-media/admin/<admin UUID>/<random UUID>.<ext>`. The bucket must remain private. Images are fully decoded/re-encoded, capped at 3 MiB and 16 million pixels, use immutable names and upload cacheControl=0. Admin previews use `/admin/media/file`, authenticate each request and return private/no-store. No draft public/signed URL is generated.

A published/due/nondeleted post can expose its associated private image through `/media/posts/:postId/:mediaId` on the web, or `/api/v1/media/posts/:postId/:mediaId` on NestJS. These routes use the anonymous repository, validate IDs, recheck parent visibility against database time/RLS and download only the exact associated private object. They return raster bytes with no-store/nosniff/sandbox, never a token, signed URL or permanent public-bucket URL. The upstream download also uses no-store and a random cache nonce. Private paths are omitted from the public domain payload.

Storage SELECT policies independently require an associated published, due, nondeleted parent, or authenticated admin membership. Both permissive and restrictive policies use this condition; raw Data/Storage API calls cannot bypass it with an ordinary JWT. Publishing or reaching the scheduled time allows delivery; hiding, archiving or moving to Trash stops subsequent requests. Content and access changes commit in PostgreSQL, without copying files between services. A failed save leaves the prior permissions intact.

If an image is shared by several posts, it remains readable while **any** parent is public. Do not attach confidential material to a public parent. Previously downloaded bytes, screenshots, third-party caches and already issued owner signed URLs cannot be revoked. Supabase's authenticated Storage endpoint also has its own cache behavior: verify staging responses and cache invalidation after hiding, beyond the app's no-store proxy. See [Supabase private Storage caching guidance](https://supabase.com/kb/troubleshooting/storage-private-bucket-files-still-accessible-after-remove-access-or-logout).

Existing `post-media` objects retain their public URLs. Database RLS cannot revoke bytes in a public bucket; hiding/Trash does not make those files confidential. Audit legacy public draft objects separately without deleting production assets or flipping bucket visibility. A draft referencing an existing public image cannot make it private.

No automatic copy, promoter, cron or privileged-key fallback exists. Public uploads/overwrites/deletes remain denied to CMS clients. Only unused private files in the current admin's namespace can be deleted with confirmation, both write gates and reference checks/locks. Lifecycle changes never delete Storage bytes. Permanent post deletion remains disabled pending an audited recoverable cleanup design.

Manual prerequisites and migration order: [post lifecycle](post-lifecycle.md), [CMS operations](admin-cms.md). Migration 002 alone intentionally refuses private publication; all of 001–003 are required for the new workflow. The isolated SQL tests validate permissions against PostgreSQL, not real Storage/CDN behavior.
