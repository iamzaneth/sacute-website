# Loading and cache behavior

Public homepage/feed routes stream their dynamic content with React Router promises, Suspense and Await. Branding, navigation, headings, search controls, notes and other static sections render first. Card placeholders preserve the layout while the database responds, expose a loading status and disable animation under reduced-motion/forced-colors preferences. Navigation between dynamic routes also shows the destination shell rather than an old page plus a loading paragraph. Contact/recruitment stay static and their route assets can prefetch on link intent.

Each public request obtains PostgreSQL time once; homepage queries and event facets share that clock within the request. Post details retain awaited server loading so missing/private posts still produce real HTTP 404 and correct article SEO metadata. Crawler document requests wait for full data and retain error HTTP statuses. Human homepage/feed document requests can start HTTP 200 streaming before the database finishes: a later failure appears as an inline error with retry, because a flushed HTTP status cannot subsequently become 503. The data resource still returns the actual 400/404/503. This is intentional; database failures never become an empty-results state.

## Validated browser memory cache

`GET /resources/content?view=home|information|scholarships|events|post` uses the same anonymous content repository and database visibility rules as SSR/API. It ignores request authentication for reads. It returns only published, due, nontrashed domain objects; no tokens or admin fields. Every request performs a fresh read under RLS, then hashes the public payload into a weak ETag. A matching `If-None-Match` returns 304 with no body. Hiding, archiving, Trash, edits, gallery changes and newly due scheduled posts change the result/tag, or return 404 for a detail. No migration or new database grant is needed.

The browser stores parsed results and ETags in RAM, keyed by view, page, keyword, category or slug. It primes this cache from SSR results, coalesces an identical in-flight fetch and shows an existing public snapshot immediately while validation runs. Lists contain full article bodies, so detail navigation can reuse a loaded list article without a blank/skeleton phase. If the complete source list is cached, category/search filters can also derive an immediate local preview; partial pages are never treated as a complete source. A successful 304 confirms the snapshot; a changed response replaces it. It retains at most 16 results, an estimated 4 MiB of serialized UTF-16 data, and five minutes without reuse. These are memory retention bounds, **not a freshness TTL**: every later navigation still validates with the server. Previously public text can remain visible during that network validation (up to the request timeout); this deliberate stale-while-revalidate presentation does not change server RLS or authorize new private content. Large payloads are displayed but not retained. Closing/reloading the tab clears the cache. No localStorage, service worker or shared server record cache is used.

Responses use `private, no-cache, max-age=0, must-revalidate`, with explicit CDN/Vercel CDN `no-store`. Fetch uses `cache:no-store` to avoid an independent HTTP-cache freshness window. The explicit application cache handles 304. Validation failure evicts the saved result and displays a retry state; stale content is not retained as an offline fallback. Late responses cannot replace the currently selected route. Entering an admin route clears the public memory cache; a generation check prevents an earlier pending response from repopulating it.

Focusing the browser tab or returning it to visibility revalidates the active public route, with duplicate focus/visibility events throttled for two seconds. It does not refresh an admin editor or discard unsaved content. An already-open public page has no background polling timer; it updates on navigation, retry or focus. Each browser tab has an independent cache. Concurrent public reads can share an in-flight request; later visits revalidate. Database and server network latency still exists during validation; caching reduces response bytes and repeated parsing, not the need to verify visibility.

Admin loaders, actions, cookies, write gates and media authorization are unchanged. Page navigation inside an authenticated admin layout shows skeletons while preserving the mounted editor; POST submissions keep their existing saving/error behavior. Admin data and private byte routes remain private/no-store and do not enter the public cache. Supabase Storage/public-image CDN behavior is unchanged.

## Verification

`tests/performance.test.mjs` exercises initial streaming with a blocked synthetic database, crawler SSR, request clock reuse, conditional responses, edits, hiding/Trash, scheduled boundaries, invalid filters and error/no-cache behavior. Browser regressions in `tests/browser/performance.spec.ts` exercise pending controls, rapid navigation, 304 reuse, stale-content eviction, retry, focus, memory retention and cache bounds. Tests use synthetic fixtures; no production data or SQL is changed.

References: [React Router streaming](https://reactrouter.com/how-to/suspense), [pending UI](https://reactrouter.com/start/framework/pending-ui), [client data](https://reactrouter.com/how-to/client-data).

Local verification on 2026-11-10: `pnpm lint`, `pnpm format:check`, `pnpm typecheck`, `pnpm test` (64 passed), `pnpm build` and `pnpm test:e2e` (52 passed). The complete browser run includes private admin navigation, rapid switching, in-flight coalescing, late responses, retention/entry bounds, trailing focus refresh, public galleries, responsive layout and accessibility. These are local fixture results; Vercel streaming/network timings remain to be verified after an owner-controlled deployment. No production SQL, content, environment settings, commits or deployment were changed.

Warm-cache regressions also block the detail/filter network response and verify the full cached article or complete-list filter preview remains visible without a skeleton. Background validation still replaces or removes obsolete content.
